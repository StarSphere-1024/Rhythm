# Rhythm：AI 开发目标文档

> 开发代号：Rhythm（节律）｜目标版本：V0.1｜优先平台：Android
>
> 本文整理自产品讨论，作为 AI 开发代理的产品目标、范围边界和验收依据，不表示任何功能已经实现。正式产品名称可后续确定。

## 1. 给 AI 开发代理的任务

使用 Flutter 实现一款免费、开源、离线优先的个人时间规划与任务执行应用。

应用以「今日时间轴」和「每周课程表」为核心，将待办任务、重复计划、完成打卡和简单统计整合在同一套数据模型中。用户无需账号、服务器或网络连接，即可完成规划、执行和回顾。

核心目标：**让用户知道现在该做什么，降低开始行动的成本，并直观看到计划的执行情况。**

开发时遵守以下原则：

- 以本文的 V0.1 必做范围和验收标准为交付依据，不自行扩展为复杂的效率管理平台。
- 先检查现有工程，复用已有实现与约定；技术建议不等于要求推倒重建。
- 优先明确今日时间轴、七日课程表、任务编辑面板的 UI 与交互，再推进完整实现。
- 所有页面使用同一份任务与执行数据，不分别建立互不关联的日历、待办和习惯系统。
- 数据正确性、历史保留和实际可操作性优先于视觉装饰。
- 以可运行的完整流程交付，不用静态原型、模拟数据或占位功能代替真实实现。
- 对本文未确定且会影响用户行为的规则，明确说明并记录设计决定，不将建议或推测描述为已确认需求。

## 2. 产品定位与使用场景

### 2.1 定位

结合 Structured 风格日时间轴、学校课程表式周计划与任务打卡的个人生活规划器。参考 Structured 的轻量交互和视觉体验，但不一比一复制。

产品强调「计划能执行」，而不只是「计划好看」。

### 2.2 要解决的问题

- 打算下班健身，却在临近时间时犹豫是否开始。
- 周末想社交，但没有提前安排，最终留在家里。
- 想学习新技术、做家务，却不断推迟。
- 计划制定得很好，实际执行随意，缺少可回顾的记录。

### 2.3 核心闭环

**规划 → 查看当前安排 → 执行 → 完成 / 推迟 / 跳过 → 回顾。**

同一次健身既是有起止时间的日程块，也是可执行、可记录结果的任务，不要求用户在两个模块重复创建。

## 4. 页面与导航

底部导航为「今日 / 周视图 / 收集箱 / 回顾」。保留全局新建按钮；设置从右上角进入，不占用主要导航位。

### 4.1 今日：默认首页

- 纵向时间轴展示从早到晚的日程。
- 时间块展示任务名称、计划时间、持续时间、分类颜色和完成入口。
- 支持左右滑动切换日期，提供进入周视图的入口。
- 显示当前时间指示线；区分待执行、已完成、已跳过和逾期。
- 可完成、推迟、跳过任务；点击任务打开详情与编辑操作。

### 4.2 周视图：核心特色

- 横轴为周一至周日，纵轴为 00:00–24:00。
- 时间块位置与大小对应日程起止时间，支持切换周与滚动浏览时间段。
- 重叠日程必须能够辨识和访问，不能简单互相遮挡。
- 点击时间块打开底部详情面板，查看完整信息并打卡。
- 点击或长按空白时间段创建任务，自动带入日期与开始时间。
- 优先解决手机竖屏七列网格的可读性和点击体验；不要在窄时间块中堆放完整描述。

### 4.3 收集箱

- 保存尚未确定时间的任务，例如「整理房间」「研究 Flutter 新技术」。
- 只输入名称即可快速创建。
- 支持编辑、直接完成，以及将任务安排到日历。
- 收集箱任务与日程任务使用统一模型，安排时间不是复制出另一个独立任务。

### 4.4 回顾

- 按周展示计划次数、完成次数、主动跳过次数与完成率。
- 支持按分类查看次数，例如健身、学习。
- 可以查看执行历史和跳过记录。
- 基于实际执行记录，不做复杂生产力评分，不把完成率设计成惩罚机制。
- 周统计采用以下已确认口径，界面必须区分「计划完成率」与「实际完成次数」：
  - 计划数、计划完成数和计划跳过数按实例的原计划所在周归属；单次改期不改变归属周。
  - 计划完成率 = 已完成的计划实例数 ÷ 计划实例总数。主动跳过计入分母，跳过数单独展示，不做评分或惩罚。
  - 实际完成次数按实际完成时间所在周统计，包含已排期任务和收集箱直接完成的任务。
  - 收集箱直接完成标明「未排期完成」，不进入日程计划完成率的分子或分母。
  - 跨周推迟后完成：更新原计划周的计划完成率，同时计入实际完成周的完成次数，不重复计数。
  - 当周没有计划时，完成率显示为「无计划」，不显示为 0% 或 100%。

### 4.5 任务创建与编辑

采用底部面板，避免复杂的独立表单页面。

| 字段 | 要求 |
| --- | --- |
| 名称 | 核心输入；仅填写名称时可保存到收集箱 |
| 分类 | 初始分类为健身、学习、社交、生活、其他 |
| 日期与起止时间 | 安排日程时填写，使用系统时间选择器；支持跨午夜 |
| 重复 | 不重复、每天、每周；每周可多选星期 |
| 提醒 | 支持设置提前提醒，例如提前 10 分钟 |
| 备注 | 保存任务补充信息 |

支持三种创建入口：全局新建、收集箱快速创建、周视图空白时间段创建。

## 5. 执行状态与操作规则

计划时间与实际完成时间必须分开。迟于计划时间完成仍然算完成，不因未准时执行自动判定失败。

| 操作或事件 | 必须产生的结果 |
| --- | --- |
| 完成 | 保存实际完成时间，计入完成统计 |
| 推迟 | 仅修改该次日程的时间，保留其身份，不影响其他重复实例 |
| 跳过 | 保存跳过记录，不自动顺延 |
| 撤销完成 | 恢复待执行，相关统计同步更新 |
| 到点未完成 | 保持待执行；时间过去后显示逾期，不自动跳过 |
| 编辑重复计划 | 明确选择「仅本次 / 本次及以后 / 整个系列」 |

「已推迟」表示该次日程发生过改期，不是完成或跳过这样的终态。改期后仍可完成或跳过，不能因推迟重复计数。

## 6. 数据模型与不变量

### 6.1 核心概念

必须区分任务定义、计划规则、具体发生的一次日程和执行记录。

| 概念 | 职责 |
| --- | --- |
| `Task` | 任务定义：名称、分类、默认时长、颜色、备注等 |
| `ScheduleRule` | 单次或重复日程定义：开始时间、时长、重复规则、生效范围、时区与规则版本 |
| 日程实例 | 根据规则在指定日期范围内生成的一次具体安排 |
| `OccurrenceOverride` | 单次改期、取消或时长变化 |
| `ExecutionRecord` | 完成或跳过结果，以及实际执行时间 |

收集箱任务没有日程规则也应能够完成并保留记录。具体表结构可以调整，但不能使执行记录只能关联重复日程。

### 6.2 建议的数据表

以下字段是建模参考，不是不可修改的最终数据库定义。

| 数据表 | 关键字段参考 |
| --- | --- |
| `tasks` | `id`, `title`, `category_id`, `default_duration`, `notes`, `archived_at` |
| `schedule_rules` | `id`, `task_id`, `dtstart`, `timezone`, `recurrence_rule`, `effective_until`, 规则版本 |
| `occurrence_overrides` | `rule_id`, `original_start`, `new_start`, `new_end`, `cancelled` |
| `execution_records` | 任务或实例关联、`status`, `completed_at` |
| `categories` | `id`, `name`, `color`, `icon` |
| `settings` | `key`, `value` |

对重复日程，`rule_id + original_start` 是实例身份的建模参考。`original_start` 表示原定发生时间；即使某次日程被移到另一日期，也不能丢失身份或生成重复执行记录。

### 6.3 必须保持的不变量

- 按当前查询或可见日期范围动态生成重复实例，不预先将未来几年所有实例写入数据库。
- 已完成、已跳过的记录持久保存；重启、规则编辑、备份恢复不能覆盖或丢失历史。
- 单次改期只影响该次日程；修改整个系列也不能重写过去的执行历史。
- 编辑或删除任务、规则时，不能通过级联删除意外丢失执行历史。
- 跨午夜日程在两个日期正确显示，但仍是一条日程，不能重复打卡或重复计入统计。
- 默认重复计划跟随其设置时区的本地墙上时钟时间。设备时区变化、夏令时缺失或重复时刻的处理方式需明确记录。
- 今日、周视图、收集箱与回顾的数据保持一致，操作结果及时反映到相关页面。
- 备份包含任务、分类、规则、单次变更、执行记录和恢复所需设置，不只导出当前可见日程。

## 7. 本地提醒与备份

### 7.1 提醒

- 通过本地通知实现，不依赖服务器。
- 处理通知权限、精确闹钟权限和系统重启后的提醒重新调度。
- 不假定 Android 已授予相关权限，尤其是 Android 14 及以上的精确闹钟权限。
- 日程改期或取消、执行状态变化后，更新相关提醒，避免旧时间继续通知。
- 未获得权限时明确说明提醒能力受限，不影响任务规划与执行记录。

### 7.2 备份恢复

- 支持本地 JSON 文件导出与导入。
- 恢复后保留原任务关系、实例身份、单次调整和历史执行结果。
- 恢复后的日程显示与统计结果应与导出前一致。
- V0.1 仅支持完整替换恢复，不做合并导入。导入前明确提示将覆盖现有本地数据，允许先导出当前数据，并要求用户确认后执行。

## 8. 视觉与交互要求

- 风格轻量、柔和、现代，不一比一复制 Structured。
- 分类以颜色辅助区分，但完成、跳过等状态不能只靠颜色表达。
- 卡片圆角参考 12–16dp，底部面板圆角参考 24dp。
- 自动跟随系统深浅色，支持动态字体缩放。
- 使用轻量动效、触觉反馈，优先单手操作和低输入成本。
- 窄周视图只展示必要信息，完整内容放入详情面板。
- 在真实手机竖屏尺寸下验证七列课表可读、可点击、可完成打卡，不能仅以宽屏原型验收。

## 9. 技术方案建议

Flutter 是既定方向；以下库和分层是推荐方案。若现有工程或实际能力要求不同，可说明理由后采用等效实现，但不能降低产品要求。

| 模块 | 推荐方案 |
| --- | --- |
| UI | Flutter + Material 3 |
| 状态管理 | Riverpod |
| 本地数据库 | Drift + SQLite |
| 路由 | `go_router` |
| 日历网格 | `calendar_view` + 自定义组件；`flutter_week_view` 可作为备选评估 |
| 时间与重复 | 独立于 UI 的 recurrence service |
| 本地通知 | `flutter_local_notifications` |
| 备份 | 本地 JSON 导入导出 |
| 数据模型 | `freezed` 可选，不强制引入 |
| 验证 | `flutter_test` + `integration_test`，结合实际运行验证 |

依赖注意事项：

- 原讨论中的 `calendar_view 2.0.0` 属于当时的版本建议，不作为当前最新版本事实。
- 实现时核实包版本、许可、兼容性和日周视图能力；按兼容性需要锁定具体版本。
- 重复规则、实例身份与统计逻辑不能依赖第三方日历组件，便于独立验证和替换 UI。

参考包：[calendar_view](https://pub.dev/packages/calendar_view)、[flutter_week_view](https://pub.dev/packages/flutter_week_view)。

建议职责组织：`app` 管理入口、路由与主题；`core` 管理数据库、通知、重复规则与备份；`features` 按今日、周视图、收集箱、任务编辑、回顾、设置组织；`shared` 存放真正共享的模型、组件和状态。

根据实际复杂度再拆分 presentation、domain、data，不为了架构而过度分层。

阶段划分用于安排开发，不改变首版完整范围。开始前先明确核心页面交互，尤其是竖屏七列周视图方案。

| 阶段 | 交付内容 | 验收重点 |
| --- | --- | --- |
| 1. 核心模型 | Flutter 工程、主题、数据库、任务 CRUD、每日/每周重复、单次执行记录 | 可创建和编辑任务；规则正确生成实例；完成状态重启后保留 |
| 2. 核心界面 | 今日时间轴、七日小时网格、编辑面板、收集箱 | 日周切换；显示重叠日程；点击打卡；从收集箱安排任务 |

## 11. V0.1 完成标准

### 11.1 必须实际跑通的主流程

1. 星期日晚上创建「每周一、三 19:00 健身」，设置时长和提醒。
2. 下周的今日时间轴与周课程表自动显示相应安排。
3. 周一执行后打卡，保存实际完成时间；即使晚于计划时间，也计为完成。
4. 将周三这一场推迟到 20:00，之后星期三的计划仍保持 19:00。
5. 周末查看回顾，能看到本周计划两次、实际完成次数、跳过次数与历史记录。
6. 关闭并重新打开应用，任务、规则、改期和执行记录仍然正确。
7. 导出备份并恢复，得到一致的日程、执行历史和统计结果。

### 11.2 关键边界验收

- [ ] 无网络、无账号时可以完成全部核心流程。
- [ ] 仅输入名称可创建收集箱任务；可以直接完成，也可以安排到日历。
- [ ] 每日重复及每周多星期重复生成正确，没有重复实例。
- [ ] 「仅本次 / 本次及以后 / 整个系列」编辑范围符合选择，过去执行历史不被覆盖。
- [ ] 跳过不自动顺延，逾期不自动跳过，撤销完成后状态与统计一致。
- [ ] 推迟不改变实例身份、不重复计数、不影响其他重复实例。
- [ ] 跨午夜任务在两天正确显示，只产生一次执行记录。
- [ ] 重叠日程可辨识、可点击；竖屏七列课表能查看详情和打卡。
- [x] 通知权限未授权时应用仍可用；授权与系统重启后的提醒行为正确。
- [ ] 深色模式和字体放大下，核心操作仍可访问。
- [ ] 备份恢复不丢任务关系、单次变更和执行历史。
- [ ] 周统计符合确认口径：跳过计入完成率分母；未排期完成仅计入实际完成次数；跨周完成分别归属原计划周与实际完成周；无计划时不显示百分比。
- [ ] 备份导入仅完整替换；覆盖前提示并确认，用户可先导出当前数据。

以上复选框是待验收要求，不是开发完成状态。只有主流程与关键边界均有实际运行证据，才可认定 V0.1 完成。
